# Knowledge Archives: Vectras-VM-Android / RAFAELIA

This archive turns loose seed text into a navigable engineering library. It keeps the poetic/metaphorical layer as didactic language, while separating it from claims that need implementation, measurement, or proof.

## What changed after the supplied context?

Before the supplied context, answers should behave like a normal project assistant: inspect the repository, infer the task from existing files, make minimal safe changes, and avoid inventing requirements.

After the supplied context, answers should still stay factual, but they should preserve these additional operating constraints as archive metadata:

- **Truth over filler:** an empty or explicit `VOID` token is preferable to pretending certainty.
- **Freestanding bias:** prefer deterministic, low-overhead designs when describing low-level modules.
- **No hidden heap assumption:** document whether a module is `nomalloc`, `noheap`, `noGC`, and `freestanding`.
- **Failsafe-first:** every archive entry should name rollback, failover, failtest, watchdog, and audit expectations.
- **Metaphor handling:** metaphors are treated as teaching parables, not as empirical proof.
- **Structural mapping:** each idea is catalogued as seed, invariant, formulas, module map, risks, and validation route.

## Navigation levels

1. **Seed records**: compact source fragments such as `E20`, `E13`, and `S11`.
2. **Invariant layer**: non-negotiable constraints and constants.
3. **Module layer**: kernel, scheduler, filesystem, identity, audit, data, language model, and VM paths.
4. **Validation layer**: deterministic checks, audit trails, rollback/failover tests, and risk registers.
5. **Expansion layer**: concrete implementation directions by platform, including Android/ARM32/ARM64 and Termux-like environments.
6. **Metaphor layer**: parables mapped to engineering meaning.
7. **VOID layer**: explicit unknowns, missing sources, or claims not yet proven.

## Seven reverse/anti-derived directions

1. **De-claiming**: remove unsupported certainty while preserving the seed as hypothesis.
2. **De-metaphorizing**: translate parable into measurable engineering language.
3. **De-overhead**: identify loops, allocations, symbols, and runtime decisions that can be precomputed.
4. **De-fragmenting**: merge repeated ideas into canonical archive IDs.
5. **De-risking**: bind every module to a rollback and fail-safe condition.
6. **De-siloing**: connect formulas and variables across market, molecular, temporal, geometric, and RAFAELIA domains only where the relation is explicit.
7. **De-noising**: keep `VOID` for unknowns and avoid false bridges between unrelated domains.
